# mospolytech-schedule-backend
## Учебные планы и модули

В админке создаются `Curriculum` (программа, набор, форма обучения, срок,
версия и исходный PDF) и `CurriculumEntry` (предмет и часы по семестру
обучения, формы контроля). Группа ссылается на план. Проверенный JSON парсера
импортируется командами и HTTP API ниже. Загрузка PDF в админке сама по себе
не запускает OCR. Часы самостоятельной работы хранятся отдельно от контактных;
неизвестные часы и формы контроля сохраняются как `null`.

`Module` задаёт реальные даты и число учебных недель календарного семестра.
`LessonEvent` может ссылаться на модуль и строку плана. Подготовка нагрузки
преобразует явно выделенные часы модуля в `pairs_per_week`. Само распределение
семестровых часов по модулям пока задаёт пользователь.

В `POST /api/schedule/generate/` можно передать `module` (ID). Генерируются
занятия выбранного модуля и общие занятия семестра без модуля. Если в семестре
есть модульные занятия, модуль обязателен. Сетка `WeekPattern` пока общая
для семестра; результат остаётся недельным шаблоном, а не календарём дат.

Аудитории связаны с корпусами (`Building`) и локациями (`Location`).
`is_active=False` исключает помещение из генерации. Тип и оборудование
пока информационные поля; ограничения по оборудованию, переходам и выбор
преподавателей не реализованы.

Повторные результаты можно хранить с `clear_previous=false`.
При `clear_previous=true` старые пары выбранного периода удаляются только
после полного успешного решения без пропущенных событий. Утверждение
действующей версии пока не реализовано. Старые данные без новых связей
сохраняют прежнее поведение.

### Импорт учебного плана

Примените миграции, включая `0009`. Для `curriculum.json` парсера
(`schema_version=1`) создайте файл проверки `curriculum-review.json`:

```json
{
  "reviewed": true,
  "source_sha256": "SHA-256 из document.source.sha256",
  "duration_months": 48,
  "version": "1",
  "entries": [
    {"source_row": 22, "semester_number": 7, "activity_kind": "REGULAR"}
  ]
}
```

`source_row` — значение поля из JSON, а не порядковый номер в PDF.
Выбираются только проверенные строки и семестры. `activity_kind` обязателен:
`REGULAR`, `PD` или `PE`; ПД и физкультура не превращаются в обычные пары группы.
Элективы также выбираются явно. Для нечитаемых или неразделённых по семестрам
значений можно задать `overrides`, например `{"lecture_hours": 18}`.
Допустимы поля часов и `has_exam`, `has_credit`, `has_graded_credit`.
Общие часы многосеместровой дисциплины автоматически не делятся.

```sh
uv run python manage.py import_curriculum curriculum.json --review curriculum-review.json
```

HTTP-эквивалент — `POST /api/schedule/curricula/import/` с телом
`{"document": <содержимое curriculum.json>, "review": <содержимое файла проверки>}`.
Ответ содержит `curriculum_id`, `entry_ids`, число созданных/обновлённых строк
и число невыбранных исходных строк. Запросы доступны администраторам приложения.

Программа, профиль, год набора, форма и версия определяют учебный план.
Предмет сопоставляется по точному имени; при нескольких совпадениях требуется
`subject_id`. Год набора берётся из источника: план 2025 года нельзя незаметно
использовать для группы набора 2024. Исходные значения, исправления и SHA-256
сохраняются у строк. Повторный импорт обновляет выбранные строки, в том числе
исправленный код той же исходной строки; невыбранные и ручные записи сохраняются.
Импорт, превышающий уже распределённые часы, откатывается целиком.

### Подготовка нагрузки группы в модуле

Свяжите группу с импортированным планом через поле `curriculum`. Для подготовки
нужны студенты группы, преподаватели и календарный `Module`. Номер семестра
обучения передаётся отдельно от ID календарного семестра.

Пример `module-load.json` (ID условные):

```json
{
  "semester_number": 5,
  "academic_hours_per_pair": 2,
  "replace": false,
  "entries": [
    {"curriculum_entry_id": 12, "lesson_type": "LECTURE", "academic_hours": 18, "teacher_id": 3},
    {"curriculum_entry_id": 12, "lesson_type": "PRACTICE", "academic_hours": 18, "teacher_id": 4}
  ]
}
```

```sh
uv run python manage.py prepare_module_load module-load.json --group 1 --module 1
```

HTTP-эквивалент — `POST /api/schedule/groups/1/prepare-load/`: содержимое файла
плюс `"module": 1`. Ответ содержит `event_ids`, число созданных, обновлённых
и удалённых событий и сумму выбранных академических часов.

Расчёт: `пары в неделю = часы модуля / (академические часы пары × учебные недели)`.
Например, 18 ч / (2 × 9) = 1 пара. Остаточные пары и чередование недель пока
не поддерживаются: вместо округления возвращается ошибка. Сумма часов одного
типа по модулям проверяется против семестровых часов плана отдельно для каждой
группы. Преподаватель назначается явно. Для лекции создаётся поток одной группы;
автоматического объединения разных групп в общий поток пока нет.

Повторная подготовка обновляет свои события без дубликатов. `replace=true`
также удаляет невыбранные события этой подготовки в данном модуле/семестре
обучения; ручные занятия сохраняются. Через подготовку нельзя переписать или
удалить событие, уже использованное в расписании. Изменение учебных недель после
подготовки блокирует генерацию до повторной подготовки согласованной нагрузки.

После подготовки используйте обычный `POST /api/schedule/generate/` с
`semester`, `module` и `clear_previous=false`. Фиксированная ПД импортируется
отдельно по правилам ниже и учитывается тем же запуском. Тест
`test_end_to_end_30_students_different_pd_and_two_lectures` проверяет полный путь
на синтетическом плане набора 2024, группе 241-3210 и 30 вымышленных студентах
с шестью разными ПД. Это проверка механизма, а не реального плана этой группы.

## API чтения расписания

После `POST /api/schedule/generate/` сохраните `id` из ответа и передавайте
его как `run_id` во все представления одного расписания:

```text
GET /api/schedule/schedule/students/1/?run_id=10
GET /api/schedule/schedule/teachers/3/?run_id=10
GET /api/schedule/schedule/groups/1/?run_id=10
GET /api/schedule/schedule/streams/2/?run_id=10
GET /api/schedule/schedule/groups/?run_id=10
```

ID условные. Последний маршрут возвращает сводку всех занятий запуска.
Студент и преподаватель получают проекции одного результата; чтение не запускает
решатель и не изменяет БД. `clear_previous=false` при генерации сохраняет пары
предыдущих вариантов.

**Изменение контракта:** маршруты `/schedule/...` возвращают объект вместо
прежнего массива пар. Клиенту нужно читать следующие поля:

| Поле | Содержимое |
| --- | --- |
| `run` | ID, семестр, модуль, статус, дата создания и сообщение выбранного запуска; `null`, если результата периода нет |
| `scheduled_classes` | Обычные пары и генерируемая ПД: время слота, предмет, формат, преподаватель, аудитория, локация и связи по ID |
| `fixed_pd_snapshot` | Фиксированная ПД с буквальным временем, датами, местом, преподавателем и подходящими участниками |
| `issues` | Предупреждения/ошибки по занятиям выбранного носителя и общие проблемы запуска |

В `scheduled_classes` добавлены `format`, `subject_id`, `teacher_id`, `group_id`,
`stream_id`, `project_id`, `group_ids`, `student_ids`. У общих пар состав задаётся
через `group_ids`; `student_ids` заполнен для генерируемой ПД. Для онлайн-пары
`room=null`. Если время старого слота не задано, `slot_start_time`/`slot_end_time`
остаются `null`. Порядок — день недели, номер пары, ID.

В `fixed_pd_snapshot` есть `run`, `session_id`, `project_id`, `project_title`,
`lesson_type=PD`, `format=ONSITE`, `day_of_week`, `start`, `end`, `date`,
`occurrence_dates`, `teacher_id`/`teacher_name`, `room_id`/`room_name`,
`location_name`, `student_ids`, `participant_group_ids`, `travel_buffer_minutes`,
`place_details` и `source`. Внешнее место может иметь `room_id=null`:
подпись берётся из `place_details.raw`. Для ключа карточки ПД используйте
пару `(run, session_id)`, для обычной пары — `id`. Дни кодируются от 0 (пн)
до 5 (сб); сортировка ПД — по дню и времени. Время ПД не округляется до слотов.

ПД в ответе группы относится только к перечисленным в `student_ids` студентам
этой группы. В ответе студента остаётся только его ID; ПД других студентов
не включается. Лекционный поток получает только лекции, без ПД своих групп.
Преподаватель получает свои пары, в том числе генерируемую ПД с руководителем
проекта, если у события не задан отдельный преподаватель.

Фиксированная ПД читается из сохранённого снимка, даже если выбор проекта
впоследствии изменился. Новые снимки также сохраняют группу каждого участника
и подписи преподавателя/комнаты/локации. У старых снимков подписи и принадлежность
участников к группе дополняются текущими справочниками. Общие пары и состав
генерируемой ПД по-прежнему связаны с текущими сущностями: полной неизменяемой
истории для них пока нет. Dev-панель ещё не использует новый сервис чтения.

Вместо `run_id` можно передать `semester` и `module`: будет выбран последний
`SOLVED` или `PARTIAL` именно этого периода. Для немодульного расписания достаточно
`semester`; если существуют только модульные запуски, требуется `module` или
`run_id`. Имя `run` поддерживается как синоним `run_id`. При явном ID можно
просмотреть и неуспешный запуск, его статус возвращается в `run.status`.
Статус описывает весь запуск, а не только отфильтрованные занятия.

Параметр `week_pattern` фильтрует слоты и сохранённые даты ПД по чётности.
Он не выбирает другой запуск и не достраивает отсутствующие занятия.
Чужой семестр, модуль или шаблон недели, некорректные ID и конфликтующие
`run`/`run_id` дают HTTP 400; отсутствующий запуск или носитель — 404.
Пустой период даёт 200: `run=null`, остальные коллекции пусты.

История `GET /api/schedule/runs/?semester=1&module=1` поддерживает фильтр модуля
и точные счётчики обычных пар/проблем. Полный запуск доступен по `/runs/10/`.
Политика доступа прежняя: чтение `/schedule/...` открыто, справочники и история
доступны staff-пользователю. Ролевое ограничение «только своё расписание» пока
не реализовано. Схемы ответов и параметры опубликованы в `/api/schema/`
и `/api/docs/`. Отдельный dev-фронтенд может обращаться через прокси на `/api`.

## Проверка

```sh
SECRET_KEY=local-test-only DB_ENGINE=sqlite python manage.py migrate
SECRET_KEY=local-test-only DB_ENGINE=sqlite python manage.py test schedule_generator
SECRET_KEY=local-test-only DB_ENGINE=sqlite python manage.py generate_demo_schedule --time-limit 60
```

Тесты проверяют импорт плана и подготовку часов, реальный решатель, фильтрацию
модуля, отключённые аудитории, сохранение вариантов, фиксированную ПД и
пересечения с группами участников. Поток может иметь несколько лекций в неделю.
Окна студентов и преподавателей оцениваются по длительности ожидания вместе
с фиксированной ПД. Перерыв до 30 минут включительно не штрафуется. Полнота
размещения имеет приоритет перед удобством; при равном числе пар сохраняется
приоритет лекций. Одинаковые персональные составы объединяются в профили,
чтобы не дублировать модель на каждого студента. Без точного времени слотов
старые сценарии оцениваются по числу пропущенных слотов. Минимум окон не означает
ранний конец дня или оптимальное число учебных дней: эти предпочтения пока
не заданы. Дневной лимит преподавателя штрафует только генерируемые пары.

## Фиксированное расписание ПД

`FixedProjectSession` хранит назначенные интервалы проекта: день, точное время,
необязательную дату и модуль, преподавателя, место и запас на дорогу. Участники
берутся из `ProjectEnrollment`. Занятия с выбранных площадок партнёров занимают
время людей, без выбора аудитории Политеха. Университетскую комнату нужно
сопоставить явно; тогда её занятость тоже учитывается. Записи доступны в админке.

После применения миграции `0008` импортируйте проверенный `pd.json` актуального
парсера. В отдельном файле сопоставлений укажите SHA-256 из `pd.json`, номера
строк проектов источника и **существующие ID** приложения. Например:

```json
{
  "reviewed": true,
  "source_sha256": "SHA-256 из поля source.sha256 выгрузки",
  "projects": [
    {"source_number": 6, "project_id": 12, "teacher_id": 8},
    {"source_number": 18, "project_id": 27, "teacher_id": 9,
     "rooms": {"Пр1211": 41, "Пр1105": 42}}
  ]
}
```

Числа ID в примере условные. Ключи `rooms` — точные подписи `place_details.raw`.
Для дополнительной площадки `rooms` не задаётся. Преподаватель по умолчанию
берётся из `Project.supervisor`; имена и номера проектов автоматически не
сопоставляются. `reviewed=true` подтверждает проверку именно выбранных записей,
включая недельное повторение. В источнике все записи требуют сверки.

```sh
uv run python manage.py import_pd_schedule output/parser-prototype/activities/pd.json \
  --mapping pd-mapping.json --semester 1 --module 1 --travel-buffer-minutes 30
```

Запас на дорогу задаётся явно (0–240 минут). Это одинаковый буфер до/после ПД
для очных занятий, кроме занятия в той же сопоставленной комнате; маршруты
по координатам не рассчитываются. Онлайн-занятия блокируются по пересечению
времени без буфера на перемещение. Все слоты должны иметь начало и конец.

Повторный импорт обновляет выбранные проекты и модуль, удаляет их устаревшие
импортированные интервалы и сохраняет ручные записи. Другие проекты остаются
без изменений; число несопоставленных проектов выводится отдельно. При ошибке
выбранный набор не изменяется. Неопределённые переносы/примечания без готового
интервала, подгруппы без состава и замены преподавателей требуют ручного разбора;
импорт останавливается с сообщением, сохраняя прежние данные.

Обычный `POST /api/schedule/generate/` автоматически учитывает эти записи.
Для проектов с фиксированным расписанием дополнительные пары ПД не генерируются.
Пересечения запрещены для участников, их общих пар группы/потока и преподавателя.
Два проекта с непересекающимися студентами одной группы могут идти одновременно.
Снимок учтённых занятий и состава сохраняется в `GenerationRun.fixed_pd_snapshot`
и возвращается API отдельно от сгенерированных `scheduled_classes`.

Результат пока остаётся недельным шаблоном: датированные занятия блокируют
объединение занятых интервалов выбранного периода, а не только одну неделю.
Это может уменьшить число размещённых пар. Даты вне модуля и другой чётности
не учитываются; первая учебная неделя считается от понедельника недели начала
семестра. Полноценные отмены/переносы по календарю остаются отдельной задачей.
При конфликте фиксированных занятий или отсутствии состава/преподавателя
генерация завершается ошибкой. При неполном размещении обычных пар возвращается
`PARTIAL`; прежнее расписание сохраняется.

## Линты и GitHub Actions

`.github/workflows/checks.yml` запускается на PR и push в `main`:
ошибки Python, импорты, современный синтаксис, потенциальные баги,
упрощения и соглашения Django (Ruff), проверки Django,
актуальность и применение миграций, тесты и демо-генерация. Для CI используется
Python 3.12; зависимости устанавливаются через `uv sync --locked --no-install-project`
из `uv.lock`. Форматирование и проверка типов пока не включены.

Локальный линт:

```sh
uvx ruff==0.17.0 check .
```

Для локального запрета прямого push в `main` после клонирования:

```sh
git config core.hooksPath .githooks
```

Hook проверяет именно ветку назначения, включая попытку `topic:main`.
Он действует только в настроенном клоне и может быть обойдён `--no-verify`.

### Серверная защита main

Администратор репозитория должен включить protection/ruleset для `main`:

- Require a pull request before merging.
- Require status checks: `Lint` и `Django checks` (после их первого запуска).
- Запрет force push и удаления ветки.
- Применение правил к администраторам / отсутствие bypass-исключений.

Обязательное одобрение другим человеком можно добавить отдельно, когда
состав команды позволяет его получать. Workflow сам по себе не запрещает
push: серверная защита настраивается на GitHub.

## Прототипы парсеров

Выгрузка расписаний всех групп из JSON API rasp.dmami.ru в общий и отдельные
JSON/CSV-файлы, с сохранением исходников и офлайн-повтором HAR:
[prototypes/dmami_parser](prototypes/dmami_parser/README.md).

Локальное OCR сканированного очного плана и выгрузка JSON/CSV: [prototypes/curriculum_parser](prototypes/curriculum_parser/README.md).

Разбор расписания ПД и физкультуры с выгрузкой JSON/CSV:
[prototypes/activity_parser](prototypes/activity_parser/README.md).

Парсеры сами не пишут в БД. Проверенные учебный план и ПД подключаются отдельными
командами выше. Импорт предложений физкультуры в приложение пока не реализован.
