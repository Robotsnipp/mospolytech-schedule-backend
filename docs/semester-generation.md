# Расчёт всех заданных модулей одной командой

`POST /api/schedule/semester-generations/` принимает `semester`, `group`,
`week_pattern`, `resource_profile` и тот же версионированный `settings`, что
одиночная генерация. Параметр `module` здесь отсутствует. Чтение результата —
`GET /api/schedule/semester-generations/{id}/`, список — тот же маршрут без ID
с необязательными фильтрами `semester` и `group`.

Запись `SemesterGeneration` координирует настоящие `GenerationRun`: по одному
на модуль, с сохранёнными ссылками в `SemesterGenerationModule`. Она не является
вызовом решателя. Нагрузка модулей остаётся раздельной: 14 пар в неделю первого
модуля и 11 второго не превращаются в 25 пар одной недели. Общий лимит поиска
заранее делится на целые доли между модулями, поэтому один трудный модуль не
исчерпывает бюджет остальных. Если секунд меньше, чем модулей, запрос отклоняется.

Часы считаются по сохранённой нагрузке и учебным неделям. Размер пары берётся
из `preparation_source.academic_hours_per_pair`, а при явных известных часах
может быть точно выведен как `academic_hours / (pairs_per_week * teaching_weeks)`.
Двойка не подставляется вместо неизвестного значения. Точное отношение сохраняется
в `hours_per_pair_ratio`; фактически размещённые часы вычисляются из числа
сохранённых пар этого события. Общие семестровые часы без распределения по
модулям не копируются в каждый модуль: соответствующие итоги остаются `null`,
а известная часть показывается отдельно.

`complete` означает успешное размещение подготовленной нагрузки всех **заданных
модулей**. Полнота календарного покрытия возвращается отдельно в `coverage`:
точные даты первого/последнего модуля, промежутки до первого и между модулями.
У модели семестра нет явной даты окончания; учебные недели не превращаются в
выдуманную календарную границу. Поэтому `semester_end_date` и `calendar_complete`
остаются `null`, а хвост после последнего модуля не объявляется покрытым.
Отмены, переносы и отдельное решение для каждой календарной недели не моделируются.

Перед запуском проверяются даты, непересечение модулей, наличие нагрузки,
принадлежность группы, сетки и ресурсного профиля. Входы каждого модуля сохраняются
со SHA-256: события и часы, учебные недели, составы, преподаватели, точные слоты,
фиксированная ПД, ресурсы и настройки. Снимок повторно сравнивается перед каждым
дочерним запуском и с фактическим входным снимком завершённого запуска.

Изменившиеся данные не подменяются молча. Не начатый модуль пропускается с
ошибкой. Если изменение обнаружено после реального вызова решателя, его запуск
остаётся доступным, соответствующая строка семестрового результата получает
`ERROR` и `input_changed=true`, а часы отражают фактический снимок дочернего запуска.
Старое ожидание хранится отдельно в `expected_required_hours`; такой семестровый
расчёт не получает `complete=true`. Остальные модули сохраняют собственные попытки.
История предыдущих запусков и вариантов не удаляется.

Фиксированная ПД при выбранном модуле берёт его явные календарные даты, даже
если конец модуля позже арифметической длительности учебных недель семестра.
Старый запуск без выбранного модуля сохраняет прежнюю проекцию по длительности.
