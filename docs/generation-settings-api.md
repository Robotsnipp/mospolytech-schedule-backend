# Настройки генерации и ручные варианты

Реализовано 02.11.2026 по `generation-settings-architecture.md`. Старый запрос
генерации сохраняется; новый режим явно выбирает одну группу и ресурсный профиль.

## Запуск

`GET /api/schedule/generation-options/` возвращает подготовленные периоды,
группы, сетки, `settings_defaults`, `rules_catalog` и `resource_profiles`.
Профиль ресурсов принадлежит конкретным группе и периоду. Отсутствующее правило
выключено, в том числе числовой ноль не означает выключение.

```json
{
  "semester": 3,
  "module": 5,
  "week_pattern": 3,
  "group": 3,
  "resource_profile": "generation-real-rooms-demo-v1",
  "clear_previous": false,
  "settings": {
    "schema_version": 1,
    "rules": {
      "free_days": [
        {"day": "sat", "mode": "preferred"},
        {"day": "sun", "mode": "required"}
      ],
      "earliest_start": {"value": "10:40", "mode": "required"},
      "latest_end": {"value": "17:40", "mode": "required"},
      "max_pairs_per_day": {"value": 4, "mode": "preferred"}
    },
    "search": {"time_limit_seconds": 30, "seed": 17}
  }
}
```

Числовые ID примера локальные; клиент получает их из каталога. Запрос отправляется
в существующий `POST /api/schedule/generate/`. Неизвестные поля, версии,
противоречащие старые параметры и совместный поток нескольких групп отклоняются.
Новый режим всегда сохраняет историю. Сетевой таймаут не означает отмену
серверного расчёта и не должен автоматически повторять POST.

Результат содержит `settings_snapshot`, `input_snapshot`, `validation_snapshot`.
Настройки истории читаются из снимка. У старого запуска отсутствие сведений
не заменяется новыми defaults. `solver_diagnostics` перечисляет уровни,
доказанную оптимальность и незавершённые уровни; `objective_value` нового режима
остаётся null, время относится ко всему поиску. Полнота размещения, статус
поиска и завершённость назначения аудиторий — разные признаки.

## История и ручные операции

- `GET /api/schedule/generation-history/?semester=3&module=5` — список запусков.
- `GET /api/schedule/generation-history/25/` — сохранённый результат.
- `GET /api/schedule/manual-variants/?run_id=25` — варианты этого результата.
- `GET /api/schedule/manual-variants/1/` — календарь ручного варианта.
- `POST /api/schedule/manual-variants/preview/` — проверка будущего состояния.
- `POST /api/schedule/manual-variants/` — повторная проверка и атомарное сохранение.
- `POST /api/schedule/manual-variants/rooms/` — подбор в контексте будущего состояния.

```json
{
  "run_id": 25,
  "variant_id": null,
  "changes": [
    {"class_id": 317, "slot_id": 95, "room_id": null},
    {"class_id": 329, "slot_id": 88}
  ],
  "name": "Мой вариант"
}
```

`class_id` — исходный `ScheduledClass.id`, а не ID события: у одного события
могут быть несколько пар. Обмен передаёт два изменения одновременно. Поля
дисциплины, длительности и участников менять нельзя. Для подбора помещений
добавляется `class_id` выбираемой пары. Ссылки на отсутствующие или чужие
источники дают ошибку, без подстановки последнего результата.

Ответы содержат общий календарь, `placements` и `validation` с коллекциями
`blocking`, `warnings`, `incomplete` и персональными метриками. Preview возвращает
200 и для недопустимого переноса, save — 400 с тем же отчётом. Очную пару можно
сохранить без аудитории: это разрешённая незавершённость. Известные конфликты
людей, аудиторий, вместимости, дороги и обязательных условий сохраняются.

Ручные варианты не создают `GenerationRun`, не меняют `ScheduledClass` и не
вызывают решатель. Результаты без полного входного снимка читаются, для правок
требуют нового расчёта. Старый replan нового режима явно не поддерживается.
Прежние права CRUD-маршрутов не меняются; новые операции используют политику
существующего generate, чтение — политику проекций расписания.

## Воспроизводимый ресурсный пример

На отдельной SQLite после миграций и подготовки примера без ПД выполните:

```sh
python manage.py seed_generation_settings_demo --source-group <ID_группы_демо_без_ПД>
```

Команда создаёт отдельные период, группу, нагрузку и семидневную сетку.
Существующие данные не заменяются; повторный вызов возвращает тот же профиль.
`fixtures/generation_real_rooms.json` сохраняет выбранные строки официальных
таблиц от 01.11.2026, URL, SHA, raw-коды и явное сопоставление корпусов.
Подтверждённая вместимость `Room.confirmed_capacity` неизвестна; числа мест
хранятся в профиле как допущения и включаются в снимок. `Room.capacity`
старого API не считается подтверждённым свойством университета.

Этот пример не включает ПД/физкультуру и не заявляет занятость всего вуза.
Персональная ПД, точные интервалы, буферы, различные занятые номера пар,
приоритеты пожеланий и ручные операции проверяются отдельными тестами
`test_settings_solver.py`, `test_manual_variants.py`, `test_resource_profiles.py`
и `test_generation_history.py`.
