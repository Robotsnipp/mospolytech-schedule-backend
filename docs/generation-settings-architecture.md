# Итоговая архитектура генерации и ручных вариантов

Проект первой версии, 01.11.2026. Документ описывает планируемую реализацию;
код этой версии ещё не написан. Согласованные пользовательские решения собраны
ниже, техническая структура выбрана для их реализации. История обсуждения —
[generation-settings-design.md](generation-settings-design.md), последовательность
работ и критерии приёмки — [generation-settings-implementation-plan.md](generation-settings-implementation-plan.md).

## Область

Одна учебная группа, подготовленная нагрузка выбранного периода/модуля,
недельный шаблон. Экран содержит настройки, индикатор ожидания синхронного
расчёта и сохранённый результат. Промежуточные решения решателя не транслируются.
Существующая политика доступа сохраняется; новые роли не вводятся.

Генератор размещает обычные лекции, практики и лабораторные. Дисциплины,
часы и преподаватели не меняются. Фиксированная ПД сохраняет свои время,
места и участников. Лимиты личной нагрузки, перерывов и учебных дней учитывают
общие занятия и только собственную ПД каждого студента, включая онлайн-занятия.
Одинаковые профили посещения объединяются для расчёта с сохранением веса и
обратной связи с участниками для объяснения нарушений.

Пользовательские лимиты относятся к студентам выбранной группы. Преподаватели
сохраняют отдельные существующие правила занятости и собственных ограничений;
студенческий лимит не применяется к ним неявно.

Новый интерфейс всегда передаёт выбранную группу явно. Для этой версии
нагрузка и потоки должны принадлежать одной группе. Совместный поток нескольких
групп не обрезается молча: такой сценарий отклоняется как неподдерживаемый.
Старый API совместного расчёта сохраняет прежний контракт.

## Каталог правил

У правила есть значение и режим `preferred` / `required`. Отсутствующее правило
выключено. В публичном контракте дни обозначаются `mon`…`sun`; числовые индексы
внешних источников преобразуются на входе, внутри расчёта действует одно соглашение.

| Настройка | Точная трактовка |
| --- | --- |
| Свободные дни | Выбранные дни без занятий личного расписания; для отдельных дней допустимы разные режимы |
| Начало и окончание | Первое личное занятие не начинается раньше нижней границы, последнее не заканчивается позже верхней |
| Максимум пар за день | Число различных занятых номеров пар личного расписания |
| Максимум перерыва | Каждый промежуток между последовательными личными занятиями одного дня, по точному времени |
| Желаемый корпус | Один выбранный корпус для размещаемых очных обычных занятий; онлайн и неизменяемая ПД не переназначаются |
| Максимум пар подряд | Длина серии соседних занятых номеров пар личного расписания |
| Минимум пар за день | Нижняя граница занятых номеров пар в учебный день; полностью свободный день допустим |
| Максимум учебных дней | Число дней с занятиями личного расписания |
| Максимум смен корпуса | Число переходов между последовательными очными занятиями с разными известными корпусами |

Последние четыре правила по умолчанию выключены — решение пользователя.
Для стартового примера остальные числовые пределы тоже не навязываются:
пользователь включает их явно. Начальный профиль предпочитает свободную субботу,
воскресенье исключено обязательно; остальные дни разрешены. Это изменяемые
значения начального профиля, а не скрытые запреты решателя.

Если неизменяемая ПД нарушает включённое обязательное условие, возвращается
конкретная несовместимость. Нельзя сдвинуть ПД, проигнорировать участника или
объявить такое условие выполненным. Для пожелания отступление отражается в отчёте;
генератор может уменьшать только изменяемую часть неудобства.

### Пары и точные интервалы

Пользователь подтвердил подсчёт по занятым номерам выбранной сетки. Обычная
пара занимает свой номер; ПД занимает все номера, с которыми её буквальный
интервал пересекается строго по времени. Касание границ пересечением не считается.
Объединение номеров выполняется отдельно для каждого студента и дня.

Пример: ПД 14:30–17:40 занимает номера 4 и 5 и учитывается как две занятые
пары. Одна онлайн-лекция, две практики и такая личная ПД дают пять пар.
Несколько интервалов, затронувших один номер, повторно его не добавляют.
Это показатель занятости, а не новое число контактных часов учебного плана.

ПД не округляется к границам пар. Пересечения людей/помещений, перерывы и
буферы дороги используют точные время начала/окончания. Максимальный перерыв
относится к каждому промежутку отдельно; обычные перемены входят в его длительность.
До первого и после последнего занятия перерыва нет. Буфер дороги проверяется
отдельно и не вычитается скрытно из длительности промежутка.

ПД, не пересекающую ни одного номера выбранной сетки, нельзя считать нулевой
нагрузкой. Перед применением обязательного лимита в парах нужна подходящая
сетка; иначе возвращается объяснение, что подсчёт неполон. При пожелании
непроверенная часть явно отмечается. Возможности новой недельной сетки включают
все семь дней; старые слоты и их времена не изменяются.

В последовательности очных занятий A→B→A две смены корпуса. Онлайн-занятие
корпуса не задаёт. Известное дополнительное место ПД учитывается как отдельный
пункт перемещения. При неизвестном месте соответствующая проверка остаётся
незавершённой; отсутствие сведений не означает ноль переходов.

### Приоритеты

Обязательные условия не нарушаются. Среди допустимых вариантов сначала
максимизируется размещение нагрузки, затем сохраняется приоритет размещения
лекций. Далее действует согласованный рабочий порядок пожеланий:

1. Свободные дни.
2. Границы времени.
3. Максимальный перерыв.
4. Дневная нагрузка, число пар подряд и минимальное число пар учебного дня.
5. Число учебных дней.
6. Смены корпуса.
7. Желаемый корпус.
8. Прежние предпочтения соседств предмета и общего удобства как дополнительный
   выбор между вариантами, равными по пользовательским условиям.

Числовые штрафы внутри одного уровня выражают степень отступления и число
затронутых людей. Они не могут переносить правило в другой уровень.
Старые штрафы субботы и поздних пар не добавляются второй копией к новым правилам.
Новый путь настроек имеет отдельную версию политики; старые запуски не пересчитываются.

Техническое решение: явные уровни цели и последовательная оптимизация CP-SAT
с общим лимитом времени, без произведения огромных весов всех новых уровней.
Следующий уровень начинается после доказательства оптимума предыдущего;
достигнутый результат фиксируется. При исчерпании бюджета возвращается лучший
допустимый вариант, перечисляются доказанные и незавершённые уровни. Новый этап
поиска не может уничтожить уже найденный вариант. Диагностика не объявляет
полную оптимальность, если нижние уровни не завершены.

Качество нового режима хранится вектором уровней и их диагностики. Старое
скалярное objective_value не используется для сравнения разных политик;
если единого числа нет, оно остаётся null. solve_time_seconds отражает весь
поиск, а не только последний этап.

## Модули и интерфейсы

Не вводится универсальный язык правил или система подключаемых расширений.
Достаточно конечного типизированного каталога и следующих модулей:

| Модуль | Ответственность |
| --- | --- |
| Нормализация настроек | Версии, режимы, значения, defaults и строгая проверка запросов |
| Входной снимок | Группа, события, составы посещения, сетка, ПД, пул ресурсов и допущения |
| Правила планирования | Общие определения занятости, номеров пар, перерывов, переходов и отступлений |
| Построение CP-SAT | Перевод нормализованных правил в ограничения и уровни цели |
| Проверка варианта | Проверка конкретных размещений с теми же смысслом правил и входным снимком |
| Сохранение вариантов | Атомарное применение переносов/обмена, история и выдача сохранённого результата |

Символьные ограничения и проверка готового размещения требуют разных
вычислительных реализаций. Они используют общую нормализацию и временные
определения; согласованность проверяется одними сценариями через оба пути.
HTTP-обработчики остаются тонкими. Frontend помогает заполнить форму и показать
ответ, а окончательную допустимость определяет backend.

## Данные и история

GenerationRun остаётся записью реального вызова решателя, ScheduledClass — его
размещениями. Добавляются снимки эффективных настроек, входов и проверки.
Они включают версии схемы/политики, лимит, seed, настройки поиска, времена
слотов, участников, ПД, используемые характеристики ресурсов и демодопущения.
Неизвестные настройки старых запусков не заполняются сегодняшними defaults.

Старый replan не используется для ручных операций. Если ему передан новый
запуск, он обязан наследовать его настройки и допущения через общий контракт
либо явно сообщить о неподдерживаемом режиме; сброс к defaults недопустим.

Ручной вариант — отдельная сущность со ссылкой на исходный GenerationRun,
возможный предыдущий ручной вариант, собственные размещения и отчёт проверки.
Копируются нужные для чтения подписи/время; текущие справочники не должны
молча менять смысл сохранённого результата. Выдача результата решателя и ручного
варианта имеет общий формат календаря с явным происхождением.

Статус поиска, полнота размещения, нарушения пожеланий и незавершённость
ресурсных назначений различаются. Ручная версия не получает фиктивный статус
решателя. Во всём новом пользовательском потоке история сохраняется:
`clear_previous=false`, исходные пары не редактируются и не удаляются.

### Ручные операции

До сохранения пользователь работает с копией. Доступны перенос одной пары,
обмен двух пар и назначение/очистка аудитории. Дисциплина, преподаватель,
продолжительность и состав участников остаются прежними.

Предварительная проверка и сохранение используют один модуль. При сохранении
backend заново проверяет весь будущий вариант и записывает его атомарно.
Обмен оценивается после освобождения обоих исходных размещений, без ложного
конфликта пары с самой собой. Остальные пары сохраняют свои положения;
решатель не вызывается. Варианты являются альтернативами, а не одновременными
бронированиями одних помещений.

Пересечения людей/аудиторий, известная недостаточная вместимость, буферы дороги
и проверяемые обязательные условия блокируют сохранение недопустимого переноса.
Отступления от пожеланий допускаются и показываются.

Если прежняя аудитория занята, показываются предупреждение и подходящие замены;
можно убрать назначение аудитории. Это разрешённая незавершённость ручного
варианта: очная пара сохраняется с пометкой «Нужно назначить аудиторию».
Невозможные без аудитории проверки корпуса/вместимости/дороги перечисляются
как незавершённые, а не успешные. Отсутствие аудитории у онлайн-пары нормально.

## Реальные помещения и демовместимость

Сохраняется явное сопоставление исходного обозначения с локацией, корпусом
и помещением генератора, URL/файл, время захвата, SHA, неизвестные значения
и ошибки. Для первого примера используется небольшой проверяемый набор реальных
помещений из найденных официальных таблиц и опубликованных обозначений.
Автоматическое слияние разных справочников по одному имени исключается.

Подтверждённая вместимость и допущение демосценария хранятся раздельно.
Эффективная вместимость: подтверждённая величина при её наличии, иначе явно
заданное допущение сценария. Пример пользователя допускает вымышленные 20/30/60
мест у реальных обозначений, с подписью «Допущение демо». Без обоих источников
значение неизвестно; новый автоматический расчёт требует допущения либо
подтверждённого числа, ручной выбор возможен с пометкой о непроверенности.
Случайный default Room.capacity=30 не считается подтверждением.

Для подбора «рядом» распознанный профиль обозначения выделяет корпус, этаж,
номер и суффикс. Приоритет: тот же корпус и этаж, близкий номер, другие этажи
того же корпуса. Нераспознанные названия используют только известную связь
с корпусом. Суффиксы не теряются, расстояние по коридору не обещается.
Подбор фильтрует точную занятость будущего варианта, ПД и вместимость;
существующий слотный список свободных помещений нельзя использовать как
готовый валидатор.

Каталог помещения и его занятость на выбранный период имеют разные источники.
Старый или неполный опубликованный срез не подтверждает свободу во всём вузе.
Полный учебный план и контролируемая входная нагрузка также различаются;
фактические гарантии и допущения примера показываются отдельно.

## Изменения HTTP-контрактов

Это планируемые изменения, не существующие endpoints:

- Существующий GET generation-options дополняется описанием поддерживаемой
  версии настроек, правил, диапазонов/defaults и подготовленного пула реальных
  помещений. Старые поля и просмотр старых запусков сохраняются.
- POST generate получает новый структурированный `settings`, выбранную группу
  и подготовленный ресурсный профиль. Настройки содержат правила и search;
  допущения профиля разрешаются backend и включаются в сохранённый снимок.
- Старые запросы генерации продолжают работать по прежнему контракту. Одновременные
  противоречащие старые/новые параметры отклоняются; новые неизвестные ключи,
  неподдерживаемые версии, чужие периоды/сетки/ресурсы возвращают ошибку до расчёта.
- Добавляются чтение/список ручных вариантов, предварительная проверка изменений,
  сохранение нового варианта и подбор аудитории в контексте будущего варианта.
- Запрос ручной операции явно выбирает исходный запуск либо вариант. Неверная
  ссылка не подменяется последним запуском и не превращает все комнаты в свободные.
- Ответ проверки содержит код правила, режим, затронутые занятия/профили,
  фактическое значение, предел и причину непроверенности, если она есть.

Выбор имён новых маршрутов и сериализаторов — деталь реализации в пределах
этого контракта. Основной существующий `/api/schedule/generate/` сохраняется.
