# План реализации настроек генерации и ручных вариантов

План от 01.11.2026 по
[итоговой архитектуре](generation-settings-architecture.md).
Объём: одна группа, девять видов правил, реальный каталог с демовместимостью,
ожидание расчёта, сохранённый календарь и ручной перенос/обмен. Код этой версии
ещё не реализован. Следующие этапы выполняются последовательно; внутри этапа
изменения backend и frontend проверяются на общем контракте.

## 0. Сохранить исходное состояние и повторить базовые проверки

- Работать с текущими подходящими checkout `work/generation-backend` и
  `work/generation-frontend`, предварительно перечитать их инструкции и status.
  Backend-база остаётся `exrta-main`, frontend — `extra-main-front-refactoring`.
  Исследование main не означает смену базы.
- Сохранить tracked/untracked исходники и отдельную согласованную SQLite-копию.
  Секреты и реальные личные данные не включать в публикуемые файлы. Зафиксировать
  контрольные хеши и состав run1–23 текущей демо-БД.
- Использовать отдельную БД/сценарий для изменений; старый пример без ПД,
  его default и история остаются доступными.
- Повторить актуальные backend/frontend проверки. Отдельно разобрать известную
  нестабильность `test_session_mode_frees_days`: один полный прогон падал,
  отдельный и повторный полный проходили. Не скрывать её ослаблением проверки.

Готовность этапа: есть восстановимая копия, известен исходный результат проверок,
выбраны точные пути рабочего кода и отдельной БД.

## 1. Ввести контракт настроек и сохраняемый входной снимок

Backend:

- Добавить конечные типизированные правила, режимы, версию схемы и нормализацию.
  Разделить правила, параметры поиска и ресурсные допущения. Четыре новых правила
  по умолчанию выключены; disabled не кодируется числом 0, у которого может быть
  нормальный смысл, например ноль смен корпуса.
- Расширить `api/serializers.py`, `api/generation_options.py` и
  `services/generation.py`: новые запросы явно выбирают одну группу и получают
  строгую проверку версии, ключей, пределов, периода, сетки и ресурсов.
- Сохранить старый запрос генерации; не принимать молча противоречащие друг другу
  старые и новые параметры. Не переименовывать существующий generate endpoint.
- Собирать версионируемый входной снимок на основе существующих EventSpec,
  FixedPDSpec и связей посещения. Сохранять эффективные настройки, поиск,
  времена, участников, ПД и используемые характеристики ресурсов.
- Создать миграции для новых снимков. У исторических запусков оставлять неизвестные
  сведения неизвестными. Старые результаты сохраняют просмотр; ручное редактирование
  без достаточного входного снимка требует нового расчёта с новым контрактом.
- Проверить входы существующего replan: новый запуск не должен молча терять
  настройки и ресурсные допущения. Использовать общий контракт наследования
  либо возвращать явную ошибку неподдерживаемого режима до создания результата.

Готовность этапа: настройки проходят полный HTTP → нормализация → снимок цикл;
неподдерживаемое поле возвращает понятную ошибку, новый default не меняет старый run.

## 2. Реализовать персональные правила и поиск

- Переиспользовать сбор посещения из `services/objectives.py`, сохранив обратное
  соответствие профилей студентам для отчётов. Обычные занятия и личная ПД
  образуют персональные временные линии.
- Добавить единые расчёты занятых номеров пар, серий, каждого перерыва,
  учебных дней и переходов. Счётчик ПД берётся из пересечений с сеткой,
  но проверки времени сохраняют буквальные интервалы.
- Для девяти видов правил реализовать required-ограничение и preferred-оценку.
  Проверять неизменяемые противоречия ПД до запуска поиска.
- В новом режиме заменить дублирующиеся старые предпочтения явными уровнями цели.
  Ввести последовательную оптимизацию с единым бюджетом времени и сохранением
  последнего допустимого решения. Сохранять доказанные/незавершённые уровни.
- Добавить независимую проверку конкретного размещения по тем же нормализованным
  правилам. Существующий generation_audit использовать как основу, расширив
  отсутствующие проверки вместимости, дней, переходов и пользовательских условий.
- Поддержать все семь дней в новом сценарии/паттерне, не меняя защищённые
  исторические слоты. Сохранить старый путь генерации и просмотра результатов.

Готовность этапа: реальный CP-SAT соблюдает включённые required-условия,
отличает пожелания, учитывает только личную ПД и выдаёт проверяемый отчёт;
выключенные дополнительные правила не создают новых условий.

## 3. Подготовить реальные ресурсы и воспроизводимый демосценарий

- Сохранить найденные официальные таблицы и manifest происхождения; выполнить
  явное сопоставление небольшого начального набора помещений. Сохранить исходные
  подписи вроде `4-ПР2609`, не трактуя `4-` автоматически как номер корпуса.
- Обновить `models/resources.py` и импорт ресурсов так, чтобы неизвестная
  подтверждённая вместимость могла оставаться неизвестной. Старые значения не
  объявлять подтверждёнными без источника.
- Подготовить отдельный ресурсный профиль с явно тестовыми 20/24/30/60 местами
  у выбранных реальных обозначений. Это данные сценария, не подмена каталога.
- Переиспользовать существующую подготовленную нагрузку одной группы. Новый
  отдельный профиль и пул комнат не выключают помещения глобально и не меняют
  записи старых запусков.
- Реализовать распознавание согласованного формата Пр, сохранение суффиксов
  и подбор по корпусу/этажу/номеру. Остальные схемы имеют безопасный fallback
  по явно сопоставленному корпусу.
- Фиксировать полноту входов, период, внешние ID, URL/файл, время и SHA.
  Не импортировать старый semester.json как актуальную занятость 2026 года.

Готовность этапа: воспроизводимый реальный каталог и отдельные демодопущения;
группа из 30 человек не получает комнату с эффективной вместимостью 20/24;
история прежней БД сохранена. Полнота сценария не выдаётся за полный вуз.

## 4. Обновить экран генерации

Frontend:

- Использовать существующие `pages/Generation.tsx`, `lib/generation.ts`,
  `GeneratedCalendar.tsx` и календарные адаптеры.
- Добавить форму девяти видов правил: значение, выключение и режим
  «желательно/обязательно». Для дней поддержать разные режимы; четыре новых
  настройки из последнего согласования выключены в начальном состоянии.
- Показать выбранную группу, период, источник нагрузки, реальные помещения
  и пометки о тестовой вместимости. Параметры поиска убрать в дополнительный блок.
- Синхронный POST показывает ожидание/прошедшее время. Не рисовать вымышленные
  проценты и не повторять POST автоматически после сетевого таймаута.
- После ответа показывать календарь и фактические полноту/статус/отступления;
  настройки результата брать из его снимка, а не из текущей формы.
- Сохранить исторический просмотр, представления группы и преподавателя,
  точные интервалы ПД и понятную ошибку неуспешного расчёта. Отдельный редактор
  неразмещённой нагрузки и новый персональный переключатель здесь не добавляются.

Готовность этапа: настоящий UI-запуск отправляет выбранные настройки backend,
получает сохранённый результат и не теряет старый вариант при неудаче/таймауте.

## 5. Добавить ручные варианты и операции

Backend:

- Добавить отдельные модели ручного варианта и его размещений, ссылки на исходный
  run/предыдущий вариант и отчёт проверки. Не использовать фиктивный GenerationRun.
- Реализовать чтение/список, preview, save и подбор помещений в контексте
  будущего варианта. Не менять существующие права старых CRUD-маршрутов.
- Применять перенос/обмен к копии исходного результата. Разрешать изменения
  только выбранных времени/аудитории; проверять принадлежность занятий исходнику.
- При save атомарно повторно проверить весь будущий вариант. Освободить оба
  исходных назначения обмена перед проверкой, не трогать остальные пары.
- Разрешить room=null у очной пары только как явное незавершённое назначение;
  остальные известные обязательные условия продолжать проверять.
- Подбор комнат должен учитывать людей, точные интервалы ПД, будущий вариант,
  корпус, эффективную вместимость и исключаемые исходные размещения. Неверный
  run/variant не означает «все помещения свободны».

Frontend:

- Добавить выбор занятия и команды переноса/обмена; перетаскивание может быть
  дополнением, но операции доступны также через карточку и клавиатуру.
- Показывать допустимые цели, причину запрета, предупреждения пожеланий,
  замену аудитории и действие «Пока без аудитории».
- Добавить «Сохранить вариант», отмену несохранённых правок, просмотр версий
  и возврат к исходному результату. После повторного открытия сохранять пометки.

Готовность этапа: перенос и обмен сохраняются без вызова решателя; исходник
не меняется; известный конфликт блокирует операцию; незавершённая аудитория
сохраняется и видна после повторного открытия.

## 6. Проверить весь пользовательский сценарий и зафиксировать результат

- Прогнать backend-тесты, линтер, миграции на отдельной БД и проверку отсутствия
  незаписанных изменений моделей; frontend-тесты, production build и линтер.
- Для каждого правила проверить off/preferred/required на небольшом реальном
  решении CP-SAT и сопоставить с проверкой конкретного результата.
- Проверить личную ПД разных студентов, два пересечённых номера пар,
  непрямоугольные интервалы, границы касания, выход за сетку, окна и дорогу.
- Проверить приоритеты пожеланий, общий лимит поиска, возврат сохранённого
  incumbent после таймаута и честность диагностики оптимальности.
- Проверить атомарный обмен, запрет чужих ID/подмены длительности, устаревшие
  ответы формы, ошибочный run, эффективную вместимость и сохранность исходника.
- В браузере выполнить: настроить → рассчитать → открыть → перенести → обменять
  → убрать аудиторию → сохранить → открыть повторно → вернуться к исходнику.
- Сравнить исходные строки/запуски и контрольные хеши; записать воспроизведение,
  результаты проверки и ограничения нового примера. Личные данные и авторизация
  в отчёты не включаются.

Готовность этапа: весь согласованный сценарий воспроизводится через настоящий
backend/frontend, история сохранена, допущения видны. Публикация и обновление
удалённых веток в этот план не входят.
