# Журнал фич

Сюда записывается каждая добавленная возможность: что делает, где живёт в коде,
как проверена и какие у неё ограничения. Правила, по которым строится
расписание, описаны отдельно: [SCHEDULING_RULES.md](SCHEDULING_RULES.md).

Нумерация совпадает с общим списком идей. Идеи без записи ниже пока не взяты в работу.

| № | Фича | Статус |
|---|------|--------|
| 1 | Индекс усталости и минимакс по группам | готово |
| 2 | Поездка как ресурс (буфер между локациями) | готово |
| 3 | Режим подготовки к сессии (свободные дни) | готово |
| 4 | Хронотип преподавателя | готово |
| 14 | Самовосстановление: минимальная перестройка | готово |
| 18 | Совместные окна студентов | готово |
| 19 | Свободные аудитории сейчас | готово |

Проверка: `python manage.py test schedule_generator` (57 тестов, решатель CP-SAT
запускается по-настоящему), `ruff check .`, миграции, демо-генерация.

## 1. Индекс усталости

**Что делает.** Для каждой группы и дня считается усталость: число пар, ранний
старт, поздние пары. Решатель штрафует превышение комфортного уровня и самый
тяжёлый день среди всех групп, поэтому расписание с одним ужасным днём проигрывает
ровному. Формула и веса: SCHEDULING_RULES.md, константы в `services/config.py`.

**Где.** `services/wellbeing.py` (формула), `objectives.collect_fatigue_penalties`
(решатель), `services/run_report.py` и `GET /api/schedule/runs/<id>/wellbeing/`
(отчёт по готовому запуску, нужны права администратора).

**Проверено.**
- Тест согласованности: значения переменных решателя равны `wellbeing.day_fatigue`
  на фиксированных наборах пар.
- Сценарии на решателе: избегает ранней пары при наличии альтернативы, разводит
  4 пары по двум дням поровну. Тесты краснеют, если обнулить `PENALTY_FATIGUE_PEAK`.
- Демо-данные (14 групп, 119 пар): максимальная усталость 35 при комфортном
  уровне 40, перегруженных дней нет.

**Ограничения.** Отчёт не учитывает пары ПД (они адресованы отдельным студентам).
Окна считаются отдельной метрикой, а их штраф в решателе имеет известную проблему
(`.agents/planning.md`), поэтому число окон в отчёте нельзя считать оптимальным.

## 2. Поездка как ресурс

**Что делает.** Раньше участник не мог быть на двух локациях в одном слоте. Теперь
он не может быть на разных локациях и в соседних слотах одного дня: дорога занимает
час, перерыв короче. Между такими парами нужен свободный слот. Правило жёсткое и
относится к группам, студентам и преподавателям.

**Где.** `constraints.add_location_consistency`, параметр `TRAVEL_BUFFER_SLOTS`
(0 отключает правило).

**Проверено.** Маленькая модель CP-SAT с зафиксированными аудиториями: соседние
слоты на разных локациях невозможны, через слот возможны, при буфере 0 возможны,
один слот на двух локациях по-прежнему невозможен. Сквозной тест: соседние пары на
одной локации по-прежнему ставятся. На демо-данных результат тот же: `SOLVED`, 119 пар.

**Ограничения.** Правило считает по номерам пар одного дня, а не по реальному
времени слотов. Аудитории без корпуса в правиле не участвуют.

## 3. Режим подготовки к сессии

**Что делает.** Недельный шаблон не знает дат экзаменов, поэтому режим выражен
числом дней: `free_days_per_group` (0–3) оставляет каждой группе столько свободных
дней в неделю из тех, где ей вообще можно проводить занятия. Нарушение мягкое:
полнота размещения важнее свободных дней.

**Где.** `POST /api/schedule/generate/` с полем `free_days_per_group`,
`config.PlanningPreferences`, `objectives.collect_free_day_penalties`.

**Проверено.** Без режима два события расходятся по двум дням, с `free_days_per_group=3`
оказываются в одном (на шести seed). Тест краснеет без `PENALTY_FREE_DAY_VIOLATION`.
Значения вне 0–3 отклоняются с кодом 400.

**Ограничения.** Привязки к конкретным неделям и датам экзаменов нет: это решение
для недельного шаблона. Режим не применяется к студентам ПД, только к группам.

## 4. Хронотип преподавателя

**Что делает.** Поле `Teacher.chronotype`: `EARLY` (жаворонок), `LATE` (сова),
`NEUTRAL`. Жаворонку штрафуются пары с номера 5, сове пары до номера 2 включительно.
Размещение нагрузки правило не блокирует.

**Где.** `enums.Chronotype`, миграция `0008_teacher_chronotype`, API преподавателей
отдаёт и принимает поле, `objectives.collect_chronotype_penalties`.

**Проверено.** Сова получает позднюю пару на каждом из шести seed; единственный
слот занимается независимо от хронотипа. На демо-данных пар в неудобное время
28 из 79 без правила и 3 из 79 с ним, при этом `SOLVED`, 119 пар.

**Ограничения.** Хронотип есть только у преподавателей, у студентов нет. Тест
жаворонка не отличает работу правила от случайного выбора (при равенстве решатель
берёт нижний слот), поэтому механизм доказывает тест совы.

## 14. Самовосстановление: минимальная перестройка

**Что делает.** Если преподаватель недоступен в некоторые дни недели или аудитория
закрыта, строится новый запуск, где все не затронутые пары закреплены (мягко, бонус
`PIN_BONUS`), а затронутые ищут новое место. Исходный запуск не меняется. Ответ
содержит число затронутых пар, оставшихся на месте, затронутых студентов и список
изменений по событиям.

**Где.** `services/replan.py`, `POST /api/schedule/replan/` (права администратора),
параметры `pinned` и `forbidden` у `generate_schedule`.

**Запрос.** `{"run": 1, "teacher": 4, "unavailable_days": [4]}` или
`{"run": 1, "room": 7}`; ошибки в параметрах дают 400 с причиной.

**Проверено.**
- На решателе: пары преподавателя уходят из недоступного дня, все остальные остаются
  в тех же слотах и аудиториях, `unchanged_count = всего - затронуто`, исходный
  запуск не изменился. Тесты краснеют при `PIN_BONUS = 0`.
- Закрытая аудитория больше не используется, остальное стабильно.
- Демо-данные: у преподавателя день из 5 пар, затронуто 5, на месте остались 114,
  затронуто 48 студентов, статус `SOLVED`, 7,4 с, в тот день у него 0 пар.
- Найдена и исправлена потеря пометки «перепланирование запуска #N» в `run.message`.

**Ограничения.** Замены преподавателя на другого нет, сбой выражен днями недели.
Закрепление мягкое: если старый запуск противоречит новым правилам, пары сдвигаются.
Дней у закрытой аудитории нет, она закрыта целиком.

## 18. Совместные окна студентов

**Что делает.** По списку студентов возвращает слоты недели, в которые свободны все.
Занятость берётся из выбранного запуска: пары группы, лекции потоков группы и ПД
выбранного проекта.

**Где.** `GET /api/schedule/schedule/common-free-slots/?semester=1&students=1,5,9`
(доступен без авторизации, как остальные запросы расписания), `services/social.py`.

**Проверено.** Свободные слоты одного студента, пересечение двух, учёт лекций потока
и пар ПД, период без запуска, валидация ввода (пусто, не числа, неизвестный ID,
больше 20 студентов).

**Ограничения.** Состояния нет: «друзья» не хранятся, список передаётся в запросе.
Нужно решать, кто может видеть чужую занятость: сейчас доступ такой же открытый, как
у расписания студента.

## 19. Свободные аудитории сейчас

**Что делает.** Возвращает активные аудитории, не занятые в слоте по выбранному
запуску. Момент задаётся парой `day_of_week` + `lesson_number`, временем `at` или,
если ничего не передано, текущим временем университета (Москва). Есть фильтры
`min_capacity` и `location`.

**Где.** `GET /api/schedule/schedule/free-rooms/?semester=1`, `services/rooms.py`.

**Проверено.** Занятые и отключённые аудитории исключаются, фильтр по вместимости,
`at` без часового пояса и с поясом дают один результат, момент вне пар даёт пустой
ответ с пояснением, неверные сочетания параметров дают 400.

**Ограничения.** «Сейчас» требует заполненного времени начала и конца у слотов.
Занятость считается по недельному шаблону, а не по датам: разовые переносы не видны.

## Исправления по ходу работы

- `GET /api/schedule/schedule/groups/<id>/` и `.../students/<id>/` падали с ошибкой
  сервера: фильтр `event__stream__groups_id` недопустим для связи многие-ко-многим, а
  `student.project_choice_id` не существует. Выборки вынесены в
  `services/schedule_queries.py` и покрыты тестами.
- Тест на мутацию (обнуление весов) показал два теста, которые проходили случайно,
  они переписаны на проверку по нескольким seed.

## Производительность

На демо-данных за 10 секунд решение находится и в старой, и в новой версии; новая
версия считает дольше (11,6 с против 7,4 с на одной и той же машине), потому что
модель богаче. При лимите 3 секунды обе версии не находят решения. Для демо
используйте `--time-limit` не меньше 10.
