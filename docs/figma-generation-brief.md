# Бриф для макета генерации расписания в Figma

Задача от 01.11.2026: создать редактируемый макет новой версии раздела генерации
расписания Московского Политеха. Пользователь явно попросил отдельного агента
для выполнения макета. Реализация приложения в эту задачу не входит.

Целевой файл создан в выбранной пользователем личной команде:
[Генерация расписания — Figma](https://www.figma.com/design/Hp5wd6oZ3iFbO5ONxdv8xm).

экран настроек. Дальнейшие вызовы Figma заблокированы лимитом Starter; календарь,
перенос, обмен и сохранённый ручной вариант пока не созданы.
Отчёт и подготовленные материалы продолжения:

## Пользовательский сценарий

Выбрать подготовленную нагрузку одной группы → задать условия → запустить
генерацию → дождаться результата → посмотреть недельную сетку → перенести пару
или обменять две пары → выбрать другую аудиторию либо временно очистить её →
сохранить отдельный ручной вариант → открыть его или вернуться к исходному.

Тексты на русском. Новые роли, настройка нескольких групп, трансляция поиска,
реальная авторизация, публикация расписания и редактор пропущенных занятий не нужны.
В интерфейс не выносятся названия CP-SAT, JSON-полей, миграций и технические run ID
как основной способ найти результат.

## Обязательные правила интерфейса

1. Одна выбранная группа, период/модуль и понятное происхождение входной нагрузки.
2. Девять видов настроек. Для включённой настройки — значение и выбор
   «Желательно» / «Обязательно», для выключенной — понятное неактивное состояние.
3. Четыре дополнительных настройки по умолчанию выключены.
4. ПД фиксирована; личная нагрузка включает только собственную ПД студента.
   Карточки ПД всей группы не означают обязательное посещение всех проектов.
5. Единица дневной нагрузки — занятые пары. ПД 14:30–17:40 занимает пары 4–5;
   буквальное время остаётся на карточке. Перерывы считаются точно по времени.
6. Ожидание расчёта с прошедшим временем; без вымышленных процентов и
   промежуточной анимации размещения занятий.
7. Полнота размещения, отступления от пожеланий и отсутствие назначения аудитории
   показываются отдельно. Ручной вариант не выдаётся за новый результат решателя.
8. Изменения сохраняются отдельным вариантом, исходник доступен для возврата.
9. Конфликт людей/обязательного условия блокирует перенос. Отступление от пожелания
   предупреждает. При конфликте только аудитории можно подобрать замену или
   выбрать «Пока без аудитории».
10. После сохранения и повторного открытия неназначенная аудитория остаётся
    явно выделенной: «Нужно назначить аудиторию».

## Настройки

| Настройка | Пример значения | Начальное состояние |
| --- | --- | --- |
| Свободные дни | Суббота — желательно; воскресенье — обязательно | Эти значения начального примера; остальные дни разрешены |
| Границы времени | Не раньше 09:00 / не позже 17:40 | Включаются явно; начало и конец независимы |
| Максимум пар в день | 4 | Включается явно |
| Максимум отдельного перерыва | 60 минут | Включается явно |
| Желаемый корпус | Прянишникова, корпус 2 | Включается явно, только для очных обычных занятий |
| Максимум пар подряд | 3 | Выключено |
| Минимум пар в учебный день | 2 | Выключено |
| Максимум учебных дней | 4 | Выключено |
| Максимум смен корпуса в день | 1 | Выключено |

Поиск: лимит времени, например 10/30/60 секунд, и seed в дополнительном блоке;
не делать технические параметры визуально главнее правил расписания.
Приоритет пожеланий: свободные дни → время → перерывы → дневная нагрузка/серии →
число дней → смены корпуса → желаемый корпус. Обязательные условия важнее;
среди допустимых решений полнота важнее пожеланий.

## Данные для изображения

Можно использовать группу «251-3210 · демо», 30 вымышленных участников,
пример расписания и условные дисциплины. Явно обозначить «Макет · демоданные»;
не выдавать изображённые показатели за реальный проверенный запуск. Макет с ПД
не называется существующим профилем «демо без ПД».

Для согласованности счётчиков подготовлен
[пример данных макета](figma-generation-demo-data.json): 14 обычных занятий,
два профиля по 15 студентов с личной ПД, максимум четыре занятые пары в день,
восемь очных обычных занятий. Это синтетическая иллюстрация, не результат
CP-SAT. Есть примеры переноса, обмена, предупреждения об окне и сохранения без
аудитории. Начальные выключенные правила и отдельный применённый профиль
для иллюстрации предупреждений различаются.

Реальные обозначения из источников: Пр1315, Пр1316, Пр2608, Пр2609, Пр2806,
в исходной официальной таблице они имеют подписи вида `4-ПР2609`. Их
сопоставление — задача реализации, а не доказанный макетом импорт.
Числа мест 20/24/30/60 — допущения примера. На выборе аудитории показывать
«30 мест · допущение демо». Для группы 30 человек комната на 20 мест не должна
выглядеть допустимым выбором. Пр2816 можно использовать как иллюстрацию схемы
номера, но его наличие в текущем локальном каталоге не подтверждено.

Подбор «рядом»: сначала тот же корпус/этаж и близкий номер, затем остальные
этажи корпуса. Сохранять различие Пр2815 а / Пр2815 б. Не показывать выдуманные
метры, маршруты или подтверждение глобальной свободы аудитории во всём вузе.

## Состав макета

Основной desktop ориентир 1440–1600 px. Сделать согласованный поток:

1. Настройки до запуска: все девять правил доступны, дополнительные четыре
   выключены. Можно использовать логичные группы/сворачивание, избегая стены полей.
2. Расчёт: состояние ожидания, прошедшее время, запрет случайного повторного запуска.
3. Готовое расписание: недельная сетка, номера/время пар, обычные занятия и ПД,
   краткий результат, доступ к настройкам сохранённого варианта и ручным операциям.
4. Перенос/подбор аудитории: выбранная пара, новое время, конфликт аудитории,
   свободные подходящие замены и «Пока без аудитории».
5. Обмен двух пар: понятно показаны обе пары, новые размещения, проверка результата.
6. Сохранённый ручной вариант: пометка одной неназначенной аудитории и возможность
   открыть исходник. Это может быть отдельное состояние основного экрана.
7. Один компактный экран около 390 px: настройки и основное действие, без попытки
   уместить мелкую desktop-сетку целиком.

Состояния можно объединять в аккуратные фреймы/оверлеи, если сценарий остаётся
понятным. По возможности связать ключевые переходы прототипом. Не добавлять
несогласованные возможности ради заполнения экрана.

## Визуальное направление

Продолжение существующего приложения: спокойные светлые поверхности,
сайдбар с разделами «Расписание», «Проектная деятельность», «Физкультура»,
«Кабинеты», активная «Генерация». Небольшие скругления, читаемая типографика,
плотная, но разборчивая сетка. Текущие токены:

- фон #F6F5F2, поверхность #FFFFFF, вторичная поверхность #EEEDE9;
- текст #15181D, вторичный #6B7280, граница #E6E3DC;
- акцент #4F46E5, мягкий акцент #EEF0FF;
- лекции #6366F1, практики #14B8A6, лабораторные #F59E0B, ПД #8B5CF6;
- радиус карточек около 16 px; тонкие границы и сдержанные тени;
- действующая типографика — проверить фактический CSS/default Tailwind
  ui-sans-serif/system stack; не объявлять Inter шрифтом продукта без проверки.

Сначала проверить Code Connect и доступные библиотеки Figma согласно skills.
Использовать доступные подходящие компоненты/переменные; при их отсутствии
следовать разрешённому fallback с токенами продукта. Общий UI должен состоять
из редактируемых слоёв, текста и структурированных элементов, а не скриншотов.
