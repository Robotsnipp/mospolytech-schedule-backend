# Контекст реализации планирования

## Входная нагрузка

Учебный план принадлежит программе, набору, форме обучения и версии.
Несколько групп могут использовать один план. Номер семестра обучения
в строке плана отличается от календарного семестра конкретного года.

`services/curriculum.py` импортирует выбранные проверенные строки JSON в
`CurriculumEntry` и подготавливает `LessonEvent` по явному распределению часов
группы в модуле. Контракты CLI и HTTP — в разделе «Учебные планы и модули»
корневого README. Источники и OCR — в [sources.md](sources.md).

Неизвестные часы/формы контроля остаются `null`; самостоятельная работа
отделена от занятий. Часы ПД/физкультуры не создают обычные пары группы.
Распределение по модулям и преподаватель задаются явно. Перевод часов в пары
требует целого результата без округления; автоматического чередования недель нет.
Бюджет каждого типа занятий суммируется по модулям отдельно для каждой группы.
Для лекции подготовки создаётся поток одной группы; объединение потоков вручную
несовместимо с повторной автоматической подготовкой этой записи.

Повторный импорт сохраняет невыбранные строки. Подготовка изменяет только свои
события и запрещает изменение/удаление использованных в расписании событий.
Эта защита относится к сервису подготовки; ручной CRUD/админка в целом ещё
не обеспечивают неизменяемую историю. Генерация проверяет согласованность часов
подготовки с текущим числом учебных недель модуля.

`test_curriculum_import.py` проверяет атомарность, повторный импорт, бюджет,
HTTP/CLI и реальный решатель на синтетическом плане набора 2024: 241-3210,
30 вымышленных студентов, шесть ПД и две лекции одного потока в неделю.
Это не подтверждение полноты реального плана этой группы.

## Генерация и календарь

Точка входа — `services/generation.py:run_generation`; её используют API и демо.
Генератор строит общий недельный шаблон участвующих групп выбранного модуля.
Занятия без модуля включаются как общие для семестра. При наличии модульных
занятий, в том числе фиксированной ПД, модуль требуется явно. Даты и число
учебных недель пока не разворачивают шаблон в календарные пары.
Для заочной формы нельзя предполагать календарь очного обучения.

Правила дней задаёт `services/day_rules.py`: генерируемая ПД — пн/ср,
обычные пары — вт/чт/пт/сб, ДПО и внеучебка — пн–сб.
Фиксированная ПД использует день из импортированного интервала.
`test_fixed_pd.py` отдельно проверяет интервалы с расширенным календарём,
чтобы запрет обычных пар по пн/ср не маскировал ошибки пересечений;
отдельный тест проверяет совместимость с календарём по умолчанию.

ДПО планируется на отдельную `Group.is_dpo=True` в очном или онлайн-формате.
У `Student` одна учебная группа; отдельное членство того же человека в группах
ДПО и объединение его основной нагрузки с ДПО пока не реализованы.

## Помещения и перемещения

Текущая цепочка — `Location → Building → Room`; `Campus` остался в истории
миграций. Отключённые аудитории исключаются из генерации. Тип и оборудование
пока описательные поля. Преподаватель назначается данными события/проекта.

`add_location_consistency` проверяет одну локацию участника в одном слоте.
Для последовательных обычных пар действует слотный запас `TRAVEL_BUFFER_SLOTS`;
это не расчёт маршрута по адресу. Для фиксированной ПД действует отдельный
явно заданный буфер в минутах, описанный ниже.

## Фиксированная ПД

`FixedProjectSession` задаёт готовые интервалы; `run_generation` учитывает их
автоматически. Состав берётся из `ProjectEnrollment`, преподаватель — из записи
или руководителя проекта. Общая пара группы/потока конфликтует с ПД любого её
участника, а два проекта с непересекающимися студентами одной группы совместимы.
Наличие фиксированных занятий проекта заменяет его генерируемую ПД.

Дополнительное место занимает время людей без выбора аудитории Политеха.
Университетская комната сопоставляется явно и резервируется. Буфер до/после ПД
задаётся в минутах для очных пар; в той же известной комнате переход не нужен.
Онлайн-пары проверяются по фактическому пересечению времени. У всех слотов
должны быть точные начало и конец. Маршруты по адресам не рассчитываются.

Датированные интервалы проецируются в недельный шаблон объединением занятости
за выбранный период и чётность. Это консервативно и может дать `PARTIAL`.
Полный календарь отмен и переносов отсутствует. Импорт останавливается на
неразобранных примечаниях, заменах преподавателя и подгруппах без состава.
Повторный импорт атомарно обновляет выбранные проекты/модуль, удаляет только
их устаревшие импортированные интервалы и сохраняет ручные записи.
Формат сопоставлений и команда импорта — в корневом README,
раздел «Фиксированное расписание ПД».

## Выдача результатов

Опубликованные правила rasp.dmami.ru импортируются командой
`import_dmami_schedule schedule.json` в `ScheduleImport`,
`ImportedGroupSchedule`, `ImportedLesson`. Это отдельные снимки с периодами,
исходными записями и датой источника; они не являются результатом CP-SAT и
не записываются в `ScheduledClass`/`LessonEvent`. Импорт атомарный, повтор
одинакового файла определяется SHA-256; неполные выгрузки отклоняются.
Просмотр — через Django admin; существующий API генератора их не выдаёт.
Импортированные пары имеют связь многие-ко-многим с `Teacher`.
`services/dmami_teachers.py` сопоставляет явные внешние ID либо нормализованные
подписи ФИО (без нечёткого сопоставления); вакансии сохраняются как предупреждения.
Повтор импорта заполняет связи старых записей без новых снимков.
Открытый read-only API `/api/schedule/imported/teachers/` поддерживает поиск,
а `/{id}/schedule/?import_id=...` выдаёт правила одного снимка с датой источника.
Без ID снимка выбирается последний импорт. Это не API результатов решателя.

`ScheduledClass` содержит сгенерированные пары. Фиксированная ПД хранится
отдельно в `GenerationRun.fixed_pd_snapshot`, включая состав и источники;
снимок возвращается полным сериализатором запуска в `api/crud.py`.
`api/serializers.py` реэкспортирует этот сериализатор.

`services/schedule_read.py` строит проекции одного запуска для студента,
группы, преподавателя и потока. API `/schedule/...` возвращает объект
`{run, scheduled_classes, fixed_pd_snapshot, issues}`. Контракт и параметры —
в разделе «API чтения расписания» README. `run_id` (синоним `run`) выбирает
запуск без периода; иначе нужны semester/module. Фильтр week_pattern только
сужает результат выбранного запуска. Статус относится ко всему запуску.

Фиксированная ПД фильтруется по сохранённым student_ids/teacher_id.
Группе возвращаются только её участники проекта. Новые снимки сохраняют
student_group_ids и подписи преподавателя/места; старые дополняются текущими
справочниками. Общие пары и генерируемая ПД связаны с текущими сущностями:
полная неизменяемая история ещё отсутствует. Тесты — test_schedule_api.py.
`with_schedule_details` загружает связи для сериализации без запросов на пару.
`dev_dashboard/student_view.py` пока читает только ScheduledClass;
новый сервис API к dev-панели ещё не подключён.
## Правила заботы о людях

Полный перечень жёстких и мягких правил: `docs/SCHEDULING_RULES.md`; журнал
возможностей: `docs/FEATURES.md`. Коротко:

- Дорога между локациями учитывается и для соседних слотов одного дня
  (`TRAVEL_BUFFER_SLOTS`); правило жёсткое и может оставить пару неразмещённой.
- Усталость, хронотип и свободные дни только штрафуются: они не вытесняют нагрузку.
- Режим подготовки к сессии выражен числом свободных дней в недельном шаблоне;
  привязки к датам экзаменов нет.
- Перепланирование создаёт новый запуск и не меняет исходный; закрепление пар мягкое.
  Замены преподавателя на другого нет.
- Выдача расписания студента и общие окна открыты без авторизации, как и прежний
  просмотр расписания. Права студента на свои данные пока не моделируются.

## Результаты

`clear_previous=false` сохраняет несколько запусков. При `true` старые пары
того же семестра и модуля удаляются только после `SOLVED` без пропущенных
событий. По умолчанию параметр всё ещё `true`. Целевой сценарий — черновик
и последующее утверждение; механизм утверждения пока отсутствует.

## Удобство расписания

`services/objectives.py` считает ожидание между последовательными занятиями
студента (общие пары и только его ПД) и преподавателя. Перерыв до 30 минут
не штрафуется; более длинный промежуток имеет стоимость в человеко-минутах
сверх этого порога. При отсутствии времени слотов работает оценка по пропущенным
слотам. `EventSpec.attending_student_ids` связывает общую нагрузку с персональной;
составы загружает `event_specs.py`. Одинаковые профили посещения объединяются
с весом по числу людей. Фиксированная ПД входит в профиль буквально по времени.

Приоритет цели: число размещённых пар, затем число лекций, затем ожидание и
дневная перегрузка преподавателя. Веса вычисляются из верхних границ штрафов,
поэтому ради окна нельзя потерять пару. Для bounds используй `max(var.proto.domain)`:
отрицательный индекс protobuf-контейнера в текущем runtime возвращал 0.
Регрессии на точный штраф, ПД, преподавателя, минуты и полноту — в
`test_objectives.py`; сквозные примеры используют реальный CP-SAT.

Раннее окончание дня не входит в цель. Число учебных дней штрафуется при
`free_days_per_group>0`; также учитываются усталость и хронотип из exrta-main.
Перепланирование сохраняет фиксированную ПД и её снимок. Сбой, затрагивающий
фиксированную ПД, требует исправления источника. Дневной лимит преподавателя
штрафует только генерируемые пары; недельный лимит ещё не применяется.

## Остальные известные ограничения

- Недельный лимит преподавателя хранится, но не применяется.
- `Group.semester` и флаг первого семестра описывают один период;
  постоянная группа и история её периодов пока не разделены.
- Выбор ПД рассчитан на один проект у студента; история выбора по учебным
  годам пока не моделируется. По договорённости проект выбирается на год.
- `solution.py` отображает отсутствие найденного решения, включая `UNKNOWN`
  по лимиту времени, как `INFEASIBLE`. При диагностике смотри также `run.message`
  с исходным статусом решателя. Большому демо может не хватать трёх секунд.

После исправления ограничения обнови этот список и добавь проверку конкретного
сценария. Совместное расписание проверяй с общими преподавателями, аудиториями
и участниками; отдельно проверяй полноту нагрузки и конфликты.
