# Парсеры и источники

## Карта парсеров

| Задача | Контекст и команды |
| --- | --- |
| OCR сканированного учебного плана | [curriculum_parser/README.md](../prototypes/curriculum_parser/README.md) |
| Разбор опубликованной таблицы ПД и PDF физкультуры | [activity_parser/README.md](../prototypes/activity_parser/README.md) |

Парсеры создают JSON/CSV с кандидатами для проверки. Импорт ПД реализован
отдельно в `services/pd_import.py` и `manage.py import_pd_schedule`.
Проверенный учебный план импортируется через `services/curriculum.py`,
`manage.py import_curriculum` и HTTP API; правила проверки и подготовки часов
описаны в корневом README. Импорт предложений физкультуры пока отсутствует.
Общий контракт генерации и оставшиеся ограничения — в [planning.md](planning.md).

## Сохранение исходного смысла

- Сохраняй исходный текст/ячейку или страницу, координаты и SHA-256 источника.
  Все результаты парсеров требуют проверки, включая записи без предупреждений.
- Неопределённость сохраняется явно: нечитаемое число — `null`, спорные варианты
  и примечания остаются доступными. Контрольные значения в `fixtures/` используются
  проверяющими скриптами и тестами, а не как подстановка ответа парсером.
- Время ПД сохраняется буквально; пересекающиеся стандартные пары выводятся
  отдельно. Переносы без полного интервала не превращаются в готовое расписание.
- Несколько аудиторий и подгруппы сохраняются без произвольного назначения
  студенту. Название и координаты дополнительного места могут быть неизвестны.
  Подтверждённые университетские адреса имеют `venue.source_url`; политика
  остальных мест описана в README парсера.
- Физкультура — предложения с выбором активности на месте; это не набор
  обязательных пар. СМГ помечается отдельно, допуск студента не выводится из PDF.

Подробные профили и ограничения находятся в README соответствующего парсера.
OCR текущего профиля учебного плана требует macOS и Apple Vision.
Профиль относится к набору 2025, а 241-3210 — к набору 2024. Для реальной
нагрузки этой группы нужен план её набора; синтетический тест не заменяет его.

## Кабинет и идентификаторы

По наблюдениям 20.10.2026 ручка состава проекта — `POST /cpd_api.php`,
`act=GPgetStudentsInPrj&pid=...`. В ответе наблюдались `fio`, `guid`, `grp`,
`pname`, `checked`. Смысл `checked` не подтверждён; `all=1` вернул только
текущего пользователя, поэтому этот флаг не означает глобальную выгрузку.

Проверенная вручную связь: ID кабинета `4330` — «Лаборатория интеллектуальных
систем [1]», номер проекта в опубликованном расписании `292`.
Для `4331` пользователь получил 25 записей состава; название и период неизвестны.
Ручка каталога проектов, автоматический клиент и хранение авторизации пока отсутствуют.
Доступность двух ID не подтверждает полноту и актуальность всех составов.

Различай номер проекта в таблице, ID кабинета и PK `Project` нашей БД.
Названия и варианты `[1]`/`[2]` требуют явного сопоставления.
GUID кабинета — внешний идентификатор студента, не PK `Student`.
Постоянных полей внешних ID в этих моделях пока нет.
Реальные составы участников и данные авторизации сохраняются вне коммитов;
фикстуры тестов содержат минимальные проверочные/синтетические данные.

## Проверка и дальнейшая интеграция

Команды unit-тестов и сверки реальных выгрузок — в README парсеров;
их зависимости задаются отдельно от производственных.
Исходники и результаты в игнорируемом `output/parser-prototype/` нужно
предоставить/получить заново на чистом checkout. HTML-отчёты и персональное
демо исключены из PR; сохранённые локальные материалы не являются частью приложения.

Сквозную связь импорта и генерации проверяет
`test_import_then_api_generation_returns_classes_and_fixed_pd_in_one_run`
в `schedule_generator/test_fixed_pd.py`: временная тестовая БД, реальный CP-SAT,
HTTP-запуск и проверка сгенерированных пар вместе со снимком ПД.

Следующие задачи — каталог и периоды проектов, внешние связи и обновление составов.
API выдаёт проекции одного запуска со снимком ПД; подключение фронтенда и
dev-панели остаётся отдельной задачей.
